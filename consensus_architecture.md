# Архитектура Консенсуса Энергетического Оракула (Без ключей API)

## 1. Суть проблемы в старой реализации
В предыдущей версии `enclave_oracle.py` присутствовала критическая математическая ошибка в функции `gather_and_validate`:
В один массив `prices` для расчета среднего/медианы складывались абсолютно разнородные физические величины:
* Цены LMP в долларах за МВт·ч (например, `$35.00`).
* Системный спрос от EIA в Мегаваттах (например, `98 000 МВт`).
* Чистый переток MISO NSI в Мегаваттах (например, `-7 000 МВт`).

Усреднение или фильтрация девиаций на таком массиве полностью разрушали логику консенсуса, делая оракул неработоспособным или выдающим некорректные арбитражные векторы.

---

## 2. Новая архитектура консенсуса (Разделение факторов)

Для обеспечения надежности и математической корректности мы разделяем данные на **Ценовые Фиды** (для расчета спреда) и **Факторы Уверенности/Нагрузки** (для валидации).

### А. Ценовые фиды (LMP Prices in $/MWh)

Мы используем только чистые цены для расчета спреда:
`Spread = PJM_LMP - MISO_LMP`

#### 1. Канал PJM LMP
* **Основной источник (GridStatus API):** GET-запрос к `https://app-api.gridstatus.io/front-end/v1/datasets/isos_latest/query?return_format=json&json_schema=array-of-arrays` (или точечно к датасету `pjm_lmp_real_time_5_min`).
  * *Метод авторизации:* Обход защиты (Bypass) без ключей с использованием заголовков официального фронтенда (`x-gs-session-id`, `x-gs-web-commit-hash`, `X-Cache-Eligible`).
  * *Резерв:* Динамический парсинг главной страницы `pjm.com` через `selectolax` для поиска актуального JSON-фида (метод Dynamic Discovery).

#### 2. Канал MISO LMP
* **Основной источник (MISO Public API):** `https://public-api.misoenergy.org/api/MarketPricing/GetLmpConsolidatedTable` (без ключей, используя `impersonate="chrome120"`). Дает точную цену `INDIANA.HUB`.
* **Резервный источник (GridStatus API):** `isos_latest/query` (дает цену `ILLINOIS.HUB` или `INDIANA.HUB`).

### Б. Физические факторы (Нагрузка и Спрос)

Эти данные собираются анонимно и используются для расчета **Confidence Score** (показателя уверенности от 0 до 100) и блокировки "нереальных" цен (например, если LMP ушел в экстремальные значения, но спрос в норме, это может быть ошибкой датчика).

* **PJM Demand (EIA API):** Спрос всей зоны PJM (через динамический запрос дат к EIA API).
* **MISO Demand (EIA API):** Спрос всей зоны MISO.
* **MISO NSI (misoenergy.org):** Чистый запланированный переток системы MISO.

## 3. Алгоритм работы Оракула в анклаве (TEE)

1. **Параллельный сбор данных:**
   * Запрос к GridStatus API для получения `PJM_LMP` (`PJM-RTO` или `PJM WEST HUB`).
   * Запрос к MISO API для получения `MISO_LMP` (`INDIANA.HUB`).
   * Запрос к EIA API для получения показателей спроса `PJM_Demand` и `MISO_Demand`.
2. **Валидация цен:**
   * Сравнение `MISO_LMP` из официального API MISO с ценой из GridStatus API. Если разница < 10%, берем среднее. Если GridStatus недоступен, используем только официальный API MISO (с понижением `confidenceScore`).
3. **Расчет арбитражного вектора:**
   * `spread = PJM_LMP - MISO_LMP`
   * Если `spread > threshold`: `arbitrageVector = 1` (выгодно перенести в MISO)
   * Если `spread < -threshold`: `arbitrageVector = -1` (выгодно перенести в PJM)
   * Иначе `0` (нейтрально).
4. **Кодирование и отправка:**
   * ABI-кодирование в `int256` (масштабирование на $10^6$) для отправки в смарт-контракт `FlexibleEnergyOracle.sol` через iExec PoCo.
